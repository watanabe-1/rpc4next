# Independent verification

For each deduplicated discovery candidate spawn a new verifier distinct from every discovery agent responsible for it, with separate context. When the interface permits, start without inherited conversation history and provide only scope, candidate, locations, evidence, relevant constraints and desired structured result. Never reuse the discoverer, even in a later turn. If custom agent selection is unsupported, use a fresh general subagent with the verifier instructions. Record actual agent IDs, not just role names. Parallelize independent candidates within the session limit; do not spawn unbounded agents.

The verifier actively searches for counterexamples, checks the contract and current code, and may run safe tests that do not alter project files or external state. It returns `confirmed`, `rejected`, or `uncertain` with evidence, reproduction or failure reason, impact and confidence. A failed, missing, or ambiguous response is `uncertain`; do not infer confirmation.

Discovery candidates assert a problem exists. Therefore verifier `rejected` or `uncertain` is a disagreement requiring a new arbiter distinct from discoverer and verifier, with both assessments and evidence. The arbiter investigates independently and returns `confirmed`, `rejected`, or `unresolved` with reasons; it must not use majority vote. A missing or failed arbiter leaves `unresolved`. Verifier `confirmed` permits final `confirmed` without arbitration; otherwise only a successful arbiter can decide. If independent contexts cannot be launched, mark the finding `unresolved`, record the failure, and stop its publication. Report partial work and offer a later run in a multi-agent-enabled session; do not run a separate service without authorization.
