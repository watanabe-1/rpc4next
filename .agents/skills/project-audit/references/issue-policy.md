# Issue policy and recovery

Use `gh` against an explicitly identified repository, subject to environment permissions; check `gh` availability and authentication without printing credentials. Never change permissions, bypass approval or create labels. Follow repository issue language and templates. Where an applicable issue-management skill is available, use its workflow and templates in addition to the audit-specific safeguards below. In rpc4next, use [github-issues](../../github-issues/SKILL.md): prefer its MCP tools for reads when available and use `gh api` for creation. If its MCP tools are unavailable, use `gh` for reads as described below.

For each confirmed root cause, compute and persist a stable fingerprint: SHA-256 of UTF-8 `project-audit:v1\n<repository identity lowercase>\n<normalized root-cause key>`, where the key is a stable human-reviewed identifier for the underlying defect and affected component, not a line number, severity or commit. Record the key. Use `<!-- project-audit-fingerprint: <hex> -->` in the draft body. Fingerprints assist search but do not replace root-cause review.

Before publication deduplicate within the run, then search both open and closed issues using the available issue search tools or `gh issue list --repo OWNER/REPO --state all --search "..." --limit ...` with several meaningful root-cause, component and symptom terms, and the fingerprint. Inspect candidate issue bodies and relevant closure/fix evidence. Check whether a closed fix is present and whether the bug actually recurred. Record queries, inspected links and reasoning. Search limitations, truncation, permission failures or ambiguous equivalence mean `unknown` and block publication. An equivalent existing open or closed issue is a duplicate: retain its URL, do not create another. For a confirmed recurrence of a previously fixed issue, link the closed issue and explain evidence that the issue is distinct or has recurred; do not assume closure alone establishes a recurrence. In ambiguous cases block and report.

Prepare one issue per independent root cause, including summary, severity, impact, expected and actual behavior, code locations at audited commit, reproduction or verification, evidence, possible fix, audit metadata and fingerprint. Redact secrets and sensitive exploit details; use the repository's private reporting channel where public disclosure would expose a vulnerability. Only attach labels already present in the repository. Do not create or modify labels.

Dry run saves drafts and duplicate outcomes and never calls any issue-creation tool or API. Publish requires explicit `publish=true` from the user and a final confirmed verdict, successful duplicate search, nonduplicate determination, and authorization under current policy. Before each create, checkpoint the complete draft, fingerprint and `creating` state. Prepare a JSON request file containing the exact title, body and any existing labels, then call `gh api repos/OWNER/REPO/issues --method POST --input <request.json> --jq '{number, html_url}'`. Preserve actual newlines in the body and do not interpolate untrusted text into a shell command. Immediately checkpoint the returned `html_url` and state `created` before processing another finding. If creation errors, output is lost, or the process is interrupted while `creating`, set or leave `unknown`; do not automatically retry. On resume search open and closed issues for fingerprint and inspect the results, including recent issues and the draft title/root cause. If one matching issue exists, record its URL; if multiple or the outcome cannot be established, stop and report for manual reconciliation. If absence is established after accounting for search indexing delays, repeat duplicate checks before a fresh create. This reduces duplicates but GitHub does not offer an atomic idempotency guarantee; concurrent runs require coordination and must not publish the same repository/root cause concurrently.
